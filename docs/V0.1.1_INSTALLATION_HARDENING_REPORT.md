## 2. P0-1 — privacy patch as a package resource

### Problem

`SolverConfig.privacy_patch_path` resolved
`<package parents[2]>/config/acp/cordis.patch.yml`. In a wheel install that becomes
`site-packages/config/acp/cordis.patch.yml`, but the wheel only shipped `ctf_solver/`.
The v0.1.0 independent test showed `privacy_patch_path` missing and ACP never launching
outside the repository root.

### Fix

- Canonical resource moved to
  **`ctf_solver/resources/acp/cordis.patch.yml`**, inside the Python package. The old
  repository-level `config/acp/cordis.patch.yml` was deleted; there is exactly one source
  of truth.
- `SolverConfig.privacy_patch_path` resolves the package resource in both source and
  installed modes.
- The in-tree wheel builder already discovers every file under `ctf_solver/`; the wheel now
  contains the resource (65 members: 64 hashed + RECORD) with identical bytes.
- `preflight` resolves the same package resource instead of a project-level copy.
- Missing/relative patch still fails closed in `default_acp_factory` / launch builder; no
  global Harness config is read or modified.

## 3. P0-2 — ACP failure must not silently queue Tasks

### Problem

`ManagerService.start()` recorded `_acp_error` and set `_started=True` even when ACP startup
failed. `create_task()` had no ACP readiness check; the Task was persisted and stayed
`queued` forever while CLI/MCP returned success.

### Fix

- New `AcpUnavailableError` (`reason_code=acp_unavailable`) and a pre-persistence guard in
  `create_task()`:
  - Manager not started;
  - ACP not ready after startup failure;
  - ACP process died after startup.
- CLI `task create` reports the ACP startup failure on stderr and exits 1; MCP
  `ctf_task_create` returns `isError=true` with `reason_code=acp_unavailable` and no Task
  is persisted.
- ACP crash after Task creation continues to use the existing durable failure mechanism:
  Task `interrupted`, Worker `crashed`, diagnostics/events recorded.
- Legitimate FIFO queuing (two active Workers, third waiting) is preserved and explicitly
  tested.
- No status-machine expansion beyond existing FAILED/INTERRUPTED mechanisms.

### Evidence

- `v011-installed-acp-failure.txt`: CLI exit 1, stderr
  `CTF-Solver Manager startup failed: ACP unavailable: ...`; the fail root DB has
  `tasks=0`, `workers=0`.
- `tests/test_installation_hardening.py`:
  `test_acp_startup_failure_blocks_task_creation_before_persistence`,
  `test_create_task_before_start_fails_closed`,
  `test_acp_crash_after_task_creation_is_durable_and_visible`,
  `test_two_worker_fifo_queue_is_preserved`,
  `test_cli_task_create_reports_acp_startup_failure`.
- Updated MCP degraded-control test (`test_integration_stack.py`) now expects
  `acp_unavailable` and zero persisted Tasks; runtime status remains available.

## 4. P1-1 — Windows venv PID identity

### Problem

The official Windows venv `python.exe` is a launcher/redirector: `Popen.pid` is the
launcher process, while the actual interpreter is its child (`venv Popen.pid=31960`, child
`pid=10596`, child `ppid=31960`). The old test compared `first["pid"] == client.pid`, and
the screenshot evidence used `probe.pid`; both failed under the venv.

### Fix

- MCP handshake payload now records both `pid` (actual executor) and `parent_pid`.
- The handshake test accepts exactly `pid == client.pid` or `parent_pid == client.pid`;
  this preserves the process-identity assertion rather than deleting it.
- `scripts/round2_integration.py` uses the probe's reported `process_pid` as the window
  capture target for both the project window and the E2E synthetic window.
- No PID assertion was removed, no test skipped, and the MCP handshake/token/schema checks
  remain unchanged.
